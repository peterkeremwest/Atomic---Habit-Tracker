# v0.2.7 — What happened, in plain language

Before this version, a list could carry one link for the whole list, such as a store's shopping list, and web addresses typed into an item's text were tappable. There was no tidy place to attach a link to one single item. If your shared home list had "Couch" on it, you could not point that item at the exact page where the couch is sold without cluttering the item's text with a long address. Now every item in a list, note, task with steps or shared list can carry its own link. You tap the item, and a box opens under it. If the item has no link yet, the box says so and offers "+ ADD A LINK". If it has one, the box shows a large OPEN button with the address next to it, and tapping OPEN sends you to your browser. A small ↗ after the item's text tells you from the outside that a link is waiting inside.

The box opens with a short animation, like the foldable sections but in the same terminal style as the rest of the app: it spreads open from the middle, with a small "LINK" tab sitting on its top border. Only one box is open at a time, so opening another item closes the first, and tapping the same item again closes it. Which box is open is remembered while the screen repaints, so saving a link does not make the box snap shut or replay its animation. Phones set to reduce motion skip the animation and simply show or hide the box. The checkbox next to an item still only checks it, and a web address typed inside the item's text still opens by itself when tapped, without opening the box.

Under the hood, the link is one extra field on the item, called `link`. For a private list, note or task step, the item lives inside its record on your device, so the link travels with it everywhere that record goes: editing the text keeps it, checking keeps it, undo brings it back, and it syncs to the cloud like the rest of the record. Nothing in the cloud needed to change for those. A shared list is different, because each of its items is its own row in the cloud, written by the shared-list clerk (the second Lambda function). That clerk keeps only the fields it knows about, which stops anyone from stuffing arbitrary data into the shared drawer. So it had to be taught about `link`. It now keeps the field only when it is a web address starting with http or https, and drops anything else, such as a `javascript:` address, which is a common trick. When a newer copy of an item arrives without a link, the newer copy wins, so removing a link on one phone removes it on the other too.

That change lives in the backend, so it only takes effect once the back office is updated from your own terminal with `cd backend && sam build && sam deploy`. Until then, the front end works fully for private lists, and for shared lists the link shows on the device that added it, but the cloud drops it, so the other person does not see it. After the deploy, a link added to an item on one phone shows up on the partner's phone at the next sync.

The new tests cover this from two sides. A backend test checks that both people get an item's link, that unsafe addresses are dropped, and that a newer copy without a link removes it. Two browser tests, one for private lists, notes and steps and one with two people on a shared list, check the whole path: the box opens and closes, bad addresses are refused, OPEN opens a new tab, the link survives edits and reloads, undo restores it, and the second person sees it and can remove it.
